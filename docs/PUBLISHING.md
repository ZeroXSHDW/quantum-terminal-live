# Publishing to GitHub

The repository is already structured for a direct GitHub upload. It contains no
build products, no machine-specific paths, and no file above GitHub's 100 MiB
limit (the movie is ~78 MiB).

## First push

```sh
cd quantum-terminal-live
git init -b main
git add .
git commit -m "Quantum Terminal Live 2.2"
git remote add origin git@github.com:<you>/quantum-terminal-live.git
git push -u origin main
```

GitHub Desktop works well with this folder. The **web** "Upload files" page has
a much smaller per-file limit than git and will usually reject the 78 MiB movie,
so use `git push` or GitHub Desktop for the first upload.

## What CI checks

`.github/workflows/ci.yml` runs on `macos-14`:

1. `scripts/validate.sh` — required files, shell/Python syntax, plist, README
   links, 100 MiB limit, no hard-coded home-directory paths, 8K PNG dimensions.
2. `scripts/build.sh` — compiles all five binaries and assembles the `.app`
   (including the procedurally rendered `AppIcon.icns`).
3. Smoke test — binaries exist, the icon is bundled, plist lints, ad-hoc
   signature verifies.

No secrets or external services are required.

## Large files

`Assets/*.mov` is already tracked with **Git LFS** (see the
`*.mov` rule in [.gitattributes](.gitattributes)):
the pointer lives in history and the binary is uploaded to LFS storage. If you
regenerate the movie at a higher bitrate and the LFS plan becomes a concern,
attach the file to a GitHub Release instead.

## Before making the repository public

- Confirm the artwork license is yours to publish (the scene is generated by
  `QuantumArtwork`, so the MIT license covers it).
- Check `LICENSE` attribution.
- Review `.gitignore` and `git status` for local files you do not want to ship.
- Do not commit Aerial's `/Users/Shared/Aerial` data; the installer creates it.
